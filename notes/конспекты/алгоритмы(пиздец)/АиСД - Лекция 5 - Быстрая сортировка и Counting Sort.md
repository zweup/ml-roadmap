## 1. Merge Sort против Quick Sort

| Сортировка | $T(N)$ | $M(N)$ |
|---|---|---|
| Merge Sort | $O(N\log N)$ | $O(N)$ |
| Quick Sort | $O(N\log N)^*$ | $O(1)$ |

\* звёздочка: быстрая сортировка работает за $O(N\log N)$ **не всегда** — только когда разбиение получается примерно посередине (см. раздел 6; в худшем случае $O(N^2)$).

> [!tip] «Разные сортировки — разные константы»
> Асимптотика $O(N\log N)$ одинакова, но в ней спрятаны разные константы: на практике Quick Sort обычно работает быстрее Merge Sort — не нужен буфер и меньше копирования.

> [!warning] Дополнение от меня: про память $O(1)$
> $O(1)$ здесь означает «не нужен дополнительный массив, как буфер у Merge Sort». Но рекурсия сама занимает память на стеке вызовов — в среднем порядка $\log N$ уровней, в худшем случае до $N$.

## 2. Идея Quick Sort (`Qsort`)

### 2.1. Partition (разбиение)

Выбираем **опорный элемент** (`pivot`) и перестраиваем кусок массива так, чтобы:

```
[ элементы ≤ pivot | pivot | элементы > pivot ]
```

Функция `Partition` **возвращает индекс (`id`), где оказался pivot**. Сам pivot после этого стоит на своём окончательном месте.

### 2.2. Qsort

Сортируем кусок `[left; right)` (правая граница не включается):

```
Qsort(arr, left, right):
    если left ≥ right:
        return
    id_p = Partition(arr, left, right)
    Qsort(arr, left, id_p)          // левая часть: элементы ≤ pivot
    Qsort(arr, id_p + 1, right)     // правая часть: элементы > pivot
```

Pivot (элемент `arr[id_p]`) в рекурсию не попадает — он уже на своём месте.

> [!tip] Сравни с Merge Sort
> Merge Sort: сначала делим «тупо пополам», потом сливаем (вся работа — в слиянии **после** рекурсии).
> Quick Sort: сначала хитро разбиваем (вся работа — в `Partition` **до** рекурсии), а потом сливать ничего не нужно: левая часть уже целиком ≤ правой.

## 3. Выбор опорного элемента (Pivot)

Способы выбрать `p`:

1. `p = arr[0]` — первый элемент
2. `p = arr[right - 1]` — последний элемент
3. `p = arr[(left + right) / 2]` — средний элемент
4. **медиана трёх:** `median(arr[0], arr[N/2], arr[N-1])`
5. **случайный:** `p = arr[random(left, right - 1)]`

> [!tip] Какой лучше
> От выбора pivot зависит, насколько ровно разобьётся массив (а от этого — скорость, см. раздел 6). Первый/последний элемент плохи на уже отсортированных массивах, а **случайный** pivot защищает от «неудачных» входов: ожидаемое время получается $O(N\log N)$ на любых данных.

## 4. Partition Ломуто

Идея: идём по массиву указателем `j` и «красим» элементы. Pivot заранее переносим в конец куска (`arr[right - 1]`).

```
 [ красные ≤ p | синие > p | зелёные (не обработаны) | pivot ]
   [left; i)       [i; j)       [j; right-1)            [right-1]
                   ↑ i — первый синий   ↑ j — первый зелёный
```

- $i$ — первый **синий** (первый элемент группы «> p»)
- $j$ — первый **зелёный** (первый ещё не обработанный)

**Шаг — берём зелёный элемент `arr[j]`:**
- `arr[j] > p` → он становится **синим**: просто `j++`
- `arr[j] ≤ p` → он должен стать **красным**: `swap(arr[i], arr[j])`, затем `i++`, `j++`

В конце все элементы обработаны, и нужно поставить pivot на своё место: `swap(arr[right - 1], arr[i])`.

**Алгоритм:**

```
Partition(arr, left, right):
    p = arr[right - 1]        // любой другой выбор pivot → сначала swap его в конец
    i = left
    for j = left ... right - 2:
        если arr[j] ≤ p:
            swap(arr[i], arr[j])
            i++
    swap(arr[right - 1], arr[i])
    return i                  // индекс pivot
```

$T(N) = O(N)$ — один проход по куску.

> [!tip] Как проверить себя на примере
> Возьми `[3, 8, 1, 7, 2]` (pivot = 2, последний). Красные — только `1`; в конце `swap` поставит `2` на место `i` (между `1` и остальными). Проверь, что слева от pivot — всё ≤ 2, справа — всё > 2.

> [!warning] Дополнение от меня
> Если в массиве много **одинаковых** элементов, этот вариант может работать плохо: все они ≤ p и попадают влево, разбиение получается «1 против $N-1$» (худший случай из раздела 6).

## 5. Partition Хоара

Другая схема разбиения: два указателя идут **навстречу друг другу** с концов куска.

```
 L →                          ← R
[ ... ≥p ...   P   ... ≤p ... ]
   ↕──────── swap ────────↕
```

**Алгоритм:**

```
Partition(arr, left, right):
    p = arr[(left + right) / 2]
    L = left
    R = right - 1
    пока (true):
        пока arr[L] < p:   L++        // ищем слева элемент ≥ p
        пока arr[R] > p:   R--        // ищем справа элемент ≤ p
        если L ≥ R:
            return R
        swap(arr[L], arr[R])
        L++
        R--
```

Результат: `[ ≤ p | ... | ≥ p ]`, возвращается индекс `R`.

$T(N) = O(N)$.

> [!warning] Чем Хоара отличается от Ломуто
> В конспекте не записано, как вызывать рекурсию после Хоара. Обычно у Хоара опорный элемент **не обязательно** оказывается на своём окончательном месте, а возвращённый индекс просто делит массив на две части (левая ≤ правой). Поэтому схему `Qsort(left, id_p)` / `Qsort(id_p + 1, right)` из раздела 2 нельзя без проверки переносить с Ломуто на Хоара. Уточни у преподавателя или в материалах курса, как именно делается рекурсивный вызов.
>
> Плюсы Хоара на практике: обычно меньше обменов, чем у Ломуто, и лучше с повторяющимися элементами.

## 6. Асимптотика Quick Sort

**Хороший случай** (разбиение примерно посередине):

- один `Partition` — $T(N) = O(N)$
- глубина рекурсии — $\log N$ уровней (кусок каждый раз делится примерно пополам)
- на каждом уровне суммарно обрабатывается $N$ элементов

$$T(N) = O(N\log N)$$

**Плохой случай** (pivot оказывается минимальным или максимальным элементом):

```
[ pivot ][ остальные N-1 элементов ]
          └ снова pivot — min/max → [ pivot ][ N-2 элемента ] ...
```

Кусок уменьшается всего на **1** элемент, а не вдвое. Тогда глубина рекурсии — $N$, на каждом уровне $O(N)$ работы:

$$N + (N-1) + (N-2) + \dots + 1 = O(N^2)$$

> [!important] Когда это случается
> Например, при `p = arr[0]` или `p = arr[right-1]` на **уже отсортированном** массиве: pivot всегда оказывается минимумом (или максимумом) куска. Поэтому важен выбор pivot (раздел 3) — медиана трёх или случайный элемент делают такой исход крайне маловероятным.

## 7. Counting Sort (сортировка подсчётом)

**Быстрая сортировка для особого случая:** значения — **небольшие целые числа**, например из $\{0, 1, 2, 3, 4\}$.

**Идея:** не сравниваем элементы, а просто **считаем**, сколько раз встретилось каждое значение, а потом выписываем значения по порядку.

```
arr = [...]
count = [0, 0, ..., 0]            // k + 1 элемент, k = max(arr)
for i = 0 ... N:
    count[arr[i]]++               // посчитали каждое значение
for i = 0 ... K:
    пока count[i] > 0:
        print(i)
        count[i]--
```

Значения лежат в диапазоне $0, 1, \dots, k$, где $k = \max(\text{arr})$.

**Асимптотика:** $T(N) = O(N + K)$.

> [!important] Нюанс: $K$ должно быть маленьким
> Если значения огромные (например, до $10^9$), массив `count` будет гигантским, и алгоритм станет бесполезным и по времени, и по памяти. Counting Sort хорош, только когда $K$ сравнимо с $N$ или меньше.

> [!important] Эта версия — неустойчивая
> Мы просто печатаем числа, а не переставляем сами элементы, поэтому «личности» одинаковых элементов теряются (если у элементов есть ещё какие-то поля — они не сохранятся). Устойчивая версия — в следующем разделе.

---

## 8. Устойчивый Counting Sort

```
arr    = [...]                    // N
count  = [0, ..., 0]              // k + 1
result = [...]                    // N

for i = 0 ... N:
    count[arr[i]]++               // 1) считаем, сколько раз встретилось каждое значение

for i = 1 ... K:
    count[i] += count[i - 1]      // 2) префиксные суммы

for j = N - 1 ... 0:              // 3) идём с КОНЦА
    result[count[arr[j]] - 1] = arr[j]
    count[arr[j]]--
```

**Что значат префиксные суммы.** После шага 2 число `count[v]` — это сколько элементов **≤ v**. Значит, последний элемент со значением `v` должен стоять на позиции `count[v] - 1` в итоговом массиве.

**Пример из конспекта** (значения $0, 1, 2, 3, 4$):

| значение | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| сколько раз встретилось | 5 | 8 | 9 | 1 | 5 |
| после префиксных сумм | 5 | 13 | 22 | 23 | 28 |

(всего 28 элементов; в конспекте у второй ячейки цифра читается как 7 — но $13 - 5 = 8$, так что в таблице 8.)

> [!important] Почему идём с конца — это и есть устойчивость
> Если идти по `arr` **с конца**, то из равных элементов самый правый занимает самую правую из выделенных им позиций, следующий — на единицу левее, и т.д. Относительный порядок равных элементов сохраняется.

**Итог:** $T(N) = O(N)$ (точнее $O(N + K)$), $M(N) = O(N)$ — нужен массив `result`, **устойчивая** сортировка.

## 9. Теорема о нижней границе (без доказательства)

> [!important] Теорема
> **Никакая сортировка сравнением не работает быстрее, чем $\Omega(N\log N)$.**

> [!tip] Но Counting Sort работает за $O(N)$ — это не противоречие
> Теорема касается сортировок, которые **сравнивают элементы между собой**. Counting Sort элементы не сравнивает, а использует их значения как индексы массива — поэтому на него теорема не распространяется. Платит он за это ограничением: значения должны быть небольшими целыми числами.

## Итог лекции

- **Quick Sort** = `Partition` (разбиваем вокруг pivot) + две рекурсии; $O(N\log N)$ в среднем, **$O(N^2)$ в худшем случае**, дополнительный буфер не нужен
- **Pivot** лучше выбирать медианой трёх или случайно — первый/последний элемент плох на отсортированных данных
- **Ломуто:** один указатель `j` «красит» элементы, `i` — граница красных; **Хоара:** два указателя навстречу друг другу; оба за $O(N)$
- **Counting Sort** — не по сравнениям, $O(N+K)$, хорош при маленьком $K$; **устойчивая** версия — через префиксные суммы и проход с конца
- Теорема $\Omega(N\log N)$ верна только для **сортировок сравнением**
